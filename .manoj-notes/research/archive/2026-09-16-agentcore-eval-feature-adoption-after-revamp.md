# AgentCore Evaluations Feature Adoption After the Receipts IDP Revamp

**Date:** 2026-09-16

Yes. After the revamp you can use essentially the whole AgentCore Evaluations feature set, including the third-party evaluators. The one exception is the A/B test. A few features also depend on changes beyond recording the outcome in the trace, and those are marked below.

## What the revamp includes

1. Record the outcome (saved or reviewed, policy block, total) on the trace.
2. Emit tool-call spans for the save and review calls.
3. Add a labeled golden dataset.
4. For the chat path: reuse one session per chat and give the agent conversation history, and invoke it through a named runtime endpoint.

## Feature by feature, after the revamp

| Feature | Execution mode | Adoptable? | Condition | What you can measure, and why the change enables it |
|---|---|---|---|---|
| Code-based evaluators (Lambda) | On-demand, Online, Batch, Dataset | Yes | Changes 1 and 3. These carry most of the business metrics. | **Measures:** STP rate (B1), dollar-weighted error (B2), control breaches such as auto-saves of 2,000 or more and duplicates (B3), review-queue precision (B4), cost per receipt (B6), degraded-volume share (B7). **Why:** a Lambda can only compute what is in the spans it receives. Change 1 puts the final outcome (saved or reviewed, total, policy block) into those spans, and change 3 supplies the correct answers to compare against. Degraded share and "auto-approved although the numbers don't add up" already work, because the rung and the `reconciles` flag are in the trace today. |
| `Builtin.GoalSuccessRate` with assertions | On-demand, Batch, Dataset. Not Online, because online configs take no ground truth. | Yes | Change 2. Assertions work in on-demand, batch, and dataset runs, not online. | **Measures:** whether each receipt obeyed business rules written as plain sentences, for example "a receipt of 2,000 or more must not be saved automatically" (B3). **Why:** the judge reads the conversation and tool calls. Today it sees the validator's decision but not whether the save happened or the policy blocked it, so it would report breaches that never happened. Change 2 puts the save or review call into what the judge reads. |
| Trajectory matchers (Exact, InOrder, AnyOrder) | On-demand, Batch, Dataset. Not Online, because they need an `expectedTrajectory`. | Yes | Change 2. Use InOrder or a separate expected trajectory per rung, because L2 and below skip the validator. | **Measures:** whether every receipt went through the required steps in order: extract, validate, then save or review (B3 process control), with no LLM cost. **Why:** the matchers compare the tool calls in the trace against an expected list. Today the final step is not a tool call in the trace, so a correct run looks like a skipped step. Change 2 adds it. |
| `Builtin.ToolParameterAccuracy` | On-demand, Online, Batch, Dataset | Yes | Change 2 for `save_expense`; works on `submit_expense` today. | **Measures:** whether the values the extractor passed to `submit_expense` are supported by the receipt text, for example a tip that is not printed anywhere. That gives a live early warning for B2 without needing correct answers. **Why:** it reads tool-call arguments, and `submit_expense` is already an agent tool call. On `save_expense` it adds little even after change 2, because the code copies those arguments straight from the extraction. |
| `Builtin.Correctness`, `Faithfulness`, `Helpfulness` (chat) | On-demand, Online, Batch, Dataset. `Correctness` with expected answers: not Online. | Yes | Change 4 so they only score chat sessions. | **Measures:** whether chat answers are right against an expected answer (Correctness, offline only), consistent with the data the tools returned rather than invented (Faithfulness), and useful to the person asking (Helpfulness). Together these cover query trust (B8). **Why:** they score a written reply to a user. Extraction runs have no user reply, so today their scores would mix real chat results with meaningless extraction results. Change 4 sends chat through its own endpoint, so an online config can score chat alone. |
| `Builtin.ToolSelectionAccuracy` | On-demand, Online, Batch, Dataset | Runs, but no fit | Each agent still has one tool. It only becomes meaningful if you redesign so an agent chooses between save and review itself. | **Measures:** nothing useful here. **Why:** it scores whether an agent picked the right tool from several. The extractor and validator each have exactly one tool, and the save-or-review choice is made by code. None of the four changes give an agent a choice, so there is still nothing to score. |
| **Managed third-party: `ThirdParty.DeepEval.ToolUse`** | On-demand, Online, Batch, Dataset | Yes | Change 2. The only third-party metric with a real fit on extraction. | **Measures:** an independent judgement on how each receipt was handled: given what was extracted, was saving it or sending it to review the right action. That is a live signal for review-queue precision (B4) that needs no correct answers. **Why:** ToolUse reads tool calls and their arguments. Today it can only see the validator's routing argument. Change 2 lets it see and judge the action actually taken. |
| **Managed third-party: `TaskCompletion`** | On-demand, Online, Batch, Dataset | Yes | Chat path. Works today. | **Measures:** whether each chat question actually got answered, for example "how much did I spend at Mr D.I.Y.?" gets a total rather than a deflection (B8). **Why:** it needs a real user goal in the session. Chat sessions already have one, so no change is needed. Extraction sessions have none, which is why change 4's scoping keeps it on chat. |
| **Managed third-party: `KnowledgeRetention`, `TurnRelevancy`, `ConversationCompleteness`, `GoalAccuracy`** | Online, Batch, Dataset, **Simulation**. Simulation generates multi-turn chats when real chat traffic is thin. | Yes | Change 4, since they need multi-turn chat sessions. | **Measures:** whether the chat agent keeps track of a conversation: remembers that the user said "last month" two questions earlier, stays on topic through follow-ups, and answers every question asked (B8 across a whole conversation). **Why:** today each chat question is its own session with a fresh agent, so there is no conversation to score. Change 4 keeps one session per chat and gives the agent its history, which creates the multi-turn sessions these metrics need. |
| **Managed third-party: `PIILeakage`, `Toxicity`, `Bias`, AutoEval `Security`** | On-demand, Online, Batch, Dataset | Yes, they run | No business outcome to attach to. `PIILeakage` will flag the intended behaviour of showing users their own data. | **Measures:** personal data in replies, abusive or biased language, and malicious output. **Why no business fit:** no receipt or chat metric depends on these. `PIILeakage` will score users seeing their own card and address details as a leak, and it cannot catch the real risk, another user's data, because it does not know whose data it is looking at. None of the changes alter that. |
| **Derived evaluators** (third-party or built-in base, your model) | On-demand, Online, Batch, Dataset. Inference runs on your account. | Yes | Through the API. CLI v0.28.1 can't express `derived` in `agentcore.json`. | **Measures:** the same thing as the base evaluator (for example ToolUse or GoalSuccessRate), but on a judge model and settings you choose, such as temperature 0 so the same receipt gets the same score on every run. That makes scores comparable over time and usable as a regression check. **Why:** a derived evaluator sees exactly what its base sees, so it gains whatever change 2 or 4 gives the base. |
| **Self-hosted third-party** (CLI `--3p-template-json` Lambda) | On-demand, Online, Batch, Dataset | Yes | For DeepEval or AutoEvals metrics outside the managed set. | **Measures:** library metrics that are not in the managed set, or that need your own parameters, for example AutoEvals `Factuality`, which compares an answer against an expected answer. **Why:** it is a Lambda like any code-based evaluator, so it sees what is in the spans. It benefits from changes 1 and 2 like the others, and from change 3 when the metric needs expected answers. |
| Online evaluation | Online | Yes | Scope workloads by runtime endpoint (change 4). Session filters are API-only. | **Measures:** every metric that needs no correct answers, continuously on live traffic: STP rate, control breaches, degraded share, cost, ToolUse, and chat answer quality, with extraction and chat scored separately. **Why:** online evaluation scores whatever runs through the runtime. Changes 1 and 2 give it the outcome to score, and change 4 separates chat from extraction so each config applies only the evaluators that fit its workload. |
| Batch evaluation | Batch | Yes | None. | **Measures:** the same evaluators over a past period in one run, for example re-scoring last month's receipts after adding a new evaluator, or examining a week you suspect went wrong. **Why:** batch reads the same stored traces as online evaluation, so it measures whatever changes 1 and 2 made visible. It needs no change of its own. |
| Dataset evaluation (preview) | Dataset | Yes | Change 3, plus an invoker function. Use a test user id. | **Measures:** the metrics that need correct answers: dollar-weighted error (B2), whether duplicates are caught (B3), review-queue precision before any reviewer data exists (B4), and a regression check after every code or prompt change. **Why:** production has no correct answers, so these can only be measured on receipts whose answers are already known. Change 3 provides those receipts, and the dataset runner replays them through the real pipeline. |
| Simulation (user simulation) | Simulation | Yes | Change 4, so chat keeps a session and history. Chat path only. Needs `pip install 'bedrock-agentcore[simulation]'` and an invoker that mints the identity token, as `scripts/ask.py` does. | **Measures:** how the chat agent handles realistic conversations it has not seen, driven by an LLM playing an employee with a goal, for example totalling their spend at one merchant and then following up about the most recent expense. The conversations are scored with the multi-turn chat evaluators and assertions. **Why:** real chat traffic may be too thin to evaluate, and datasets only replay scripted turns. Simulated follow-ups need an agent that remembers the conversation, which change 4 adds; today each question is a fresh session. Extraction has no conversation, so simulation does not apply there. |
| Insights (failure analysis) | Insights | Yes | Needs its own online config. Sees the save step after change 2. | **Measures:** recurring failure patterns grouped by root cause, for example many receipts failing at the save step, or many chat answers inventing amounts. **Why:** insights analyses the steps recorded in the trace. Today the extraction trace stops before the save, so failures at that step cannot appear in its findings. Change 2 makes the save step visible. |
| Recommendations | Recommendations | Yes | Needs an evaluator to optimise against. | **Measures:** suggested rewrites of the extractor's or validator's system prompt, or of tool descriptions, aimed at raising one evaluator's score, for example review-queue precision. **Why:** recommendations use an evaluator's scores as the signal, and there is no useful signal until the business-metric evaluators above exist, which depend on changes 1 to 3. Whether a code-based evaluator can drive recommendations is unverified. |
| **A/B test** | A/B test | **No** | Needs a gateway fronting the runtime, and rung selection moved into config bundles. That's a larger redesign than this revamp. | **Would measure:** whether a change, such as the L2 model rung or a new prompt, costs STP or accuracy, by splitting live traffic between two versions. **Why not:** A/B tests split traffic at a gateway in front of the runtime, between config bundles or gateway targets. Receipts go straight from the trigger Lambda to the runtime, and the rung comes from AppConfig, so there is nothing to split. None of the four changes address that. Run the golden dataset once per rung instead. |

## Third-party evaluators specifically

The revamp makes every third-party evaluator **runnable**. Whether each one is **relevant** depends on the workload:
- **Extraction:** only `ToolUse` has a real business fit.
- **Chat:** `TaskCompletion` fits today. The multi-turn metrics fit once chat keeps a session and history.

So the chat path is where the third-party evaluators pay off.
